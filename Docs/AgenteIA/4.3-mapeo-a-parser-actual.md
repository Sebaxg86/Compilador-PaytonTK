# 4.3 Mapeo del Esquema de Traduccion al Parser Actual

## Proposito

Este documento no redefine la semantica de PaytonTK ni propone una arquitectura nueva.

Su unico objetivo es mapear el esquema de traduccion de [4.1-esquema-traduccion.md](./4.1-esquema-traduccion.md) al parser actual de `SintacticoSemantico.java`, siguiendo la guia clasica descrita en [4.2-implementacion-semantica-a-codigo.md](./4.2-implementacion-semantica-a-codigo.md) y en los apuntes del Ing. Gil.

## Alcance

Este documento asume el metodo clasico del Libro del Dragon:

1. Un procedure por no terminal.
2. Un objeto `Atributos` por simbolo no terminal que participe en acciones semanticas.
3. Una variable local `Linea_BE` para cada terminal con atributos cuando dichos atributos se usen en una accion.
4. Las acciones semanticas se ejecutan exactamente en el punto `{n}` donde aparecen en la produccion.

## Limites del documento

Este documento no propone:

1. AST.
2. Visitor pattern.
3. Fase semantica separada del parser.
4. Analisis posterior en otra estructura intermedia.

Todo debe vivir dentro del parser predictivo recursivo, tal como lo pide Gil.

## Convenciones para el mapeo

En el parser actual, los no terminales con prima se implementan con sufijo `_2`:

- `ARGUMENTOS'` -> `ARGUMENTOS_2`
- `DECLARACION_VARS'` -> `DECLARACION_VARS_2`
- `PROPOSICION'` -> `PROPOSICION_2`
- `LISTA_EXPRESIONES'` -> `LISTA_EXPRESIONES_2`
- `EXPRESION'` -> `EXPRESION_2`
- `TERMINO'` -> `TERMINO_2`
- `FACTOR'` -> `FACTOR_2`

En la implementacion Java, la forma esperada de cada procedure sera:

```java
private void NO_TERMINAL(Atributos _NO_TERMINAL)
```

Cuando una produccion usa otro no terminal en el lado derecho, se declara una variable local de tipo `Atributos` para esa ocurrencia.

Cuando una produccion usa `id`, `num`, `num.num` o `literal` y alguno de sus atributos participa en una accion semantica, se salva `cmp.be.preAnalisis` en una variable local de tipo `Linea_BE` antes de `emparejar(...)`.

## Atributos minimos ya justificados por el esquema

La clase `Atributos` solo debe contener atributos que ya aparecen en el esquema de `4.1` o que son la traduccion directa de ese esquema a Java:

```java
class Atributos {
    String tipo;
    String h;
    String tmp;
    String ret;
    List<String> listaIds;
    List<String> listaTipos;
}
```

Observacion:

- `tipo`, `h`, `tmp`, `ret`, `listaIds` y `listaTipos` ya existen conceptualmente en el esquema de `4.1`.
- `funActual` y `tipoRetActual` tambien aparecen en las acciones `{5}`, `{6}` y `{7}` del esquema. Su materializacion concreta en Java puede resolverse como contexto del parser, pero no cambian el metodo clasico.

## Acciones previas fuera de los procedures

Antes de ejecutar el esquema de traduccion dentro del parser, se respetan las acciones previas ya documentadas en `4.1`:

1. Tipificacion inicial de constantes:
   - `num -> int`
   - `num.num -> float`
   - `literal -> string`
2. Registro previo de firmas de funciones:
   - nombre
   - lista de tipos de parametros
   - tipo de retorno

Estas acciones previas no sustituyen al parser ni crean una arquitectura nueva; solo preparan la tabla de simbolos para que las acciones del esquema funcionen correctamente.

## Mapeo general al parser actual

### `PROGRAMA`

- Method actual: `PROGRAMA()`
- Firma esperada: `private void PROGRAMA(Atributos _PROGRAMA)`
- Produccion: `PROGRAMA -> INSTRUCCION PROGRAMA {1} | ϵ {2}`
- Variables locales: `Atributos _INSTRUCCION`, `Atributos _PROGRAMA1`
- Acciones:
  - Si entra por `INSTRUCCION PROGRAMA`, invocar `INSTRUCCION(_INSTRUCCION)`, luego `PROGRAMA(_PROGRAMA1)`, y despues ejecutar `{1}`.
  - Si entra por vacio, ejecutar `{2}`.
- Salida semantica: `_PROGRAMA.tipo`

### `INSTRUCCION`

- Method actual: `INSTRUCCION()`

### `FUNCION`

- Method actual: `FUNCION()`
- Firma esperada: `private void FUNCION(Atributos _FUNCION)`
- Produccion: `FUNCION -> def id {5} ( ARGUMENTOS ) : TIPO_RETORNO {6} PROPOSICIONES_OPTATIVAS return RESULTADO {7} :: {8}`
- Variables locales: `Atributos _ARGUMENTOS`, `_TIPO_RETORNO`, `_PROPOSICIONES_OPTATIVAS`, `_RESULTADO`
- Terminales con atributos: `Linea_BE id`
- Acciones:
  - Salvar `id` antes de `emparejar("id")`.
  - Ejecutar `{5}` inmediatamente despues de reconocer `id`.
  - Invocar `ARGUMENTOS(_ARGUMENTOS)` y `TIPO_RETORNO(_TIPO_RETORNO)`.
  - Ejecutar `{6}` justo despues de `TIPO_RETORNO`.
  - Invocar `PROPOSICIONES_OPTATIVAS(_PROPOSICIONES_OPTATIVAS)`.
  - Despues de `return RESULTADO`, ejecutar `{7}`.
  - Al cerrar con `::`, ejecutar `{8}`.
- Salida semantica: `_FUNCION.tmp`, `_FUNCION.ret`, `_FUNCION.tipo`
- Observacion:
  - Para seguir exactamente `4.1`, este procedure debe cerrar con `::`.

## Resumen de correspondencia entre el esquema y el parser

La correspondencia esperada entre documentos es esta:

1. `4.1-esquema-traduccion.md` dice que accion semantica existe y en que punto de la produccion aparece.
2. `4.2-implementacion-semantica-a-codigo.md` dice como bajar esa produccion con acciones a un procedure Java clasico.
3. Este documento `4.3` dice en que method actual del parser cae cada produccion del esquema.

## Orden natural para implementar sin salir del metodo clasico

Si se quiere avanzar al codigo despues de este documento, el orden mas directo es:

1. Introducir `Atributos` y ajustar firmas de procedures.
2. Cablear primero `TIPO_DATO`, `TIPO_RETORNO` y `RESULTADO`.
3. Cablear `ARGUMENTOS`, `DECLARACION_VARS` y sus variantes `_2`.
4. Cablear `FACTOR`, `TERMINO`, `EXPRESION` y sus variantes `_2`.
5. Cablear `LISTA_EXPRESIONES`, `CONDICION`, `PROPOSICION` y `PROPOSICIONES_OPTATIVAS`.
6. Cerrar con `FUNCION`, `INSTRUCCION` y `PROGRAMA`.

Este orden no introduce un metodo nuevo; solo reduce riesgo al implementar el mismo esquema clasico por dependencias.
